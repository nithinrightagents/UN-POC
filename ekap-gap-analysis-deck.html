I · The system as documented02 / 11

Two applications, one stack, and a scoring engine that isn't in either of them

The load-bearing observation. EGOVSURVEY collects and EGovKB displays — but nothing in the documented architecture computes. The index that the whole exercise exists to produce is assembled in spreadsheets, then typed back into a public website by hand. Every gap in the register that follows is a consequence of that shape.

Why it compounds rather than adds

A cycle cannot start until a 2022 project is cloned (G-01) and its question set is hand-reordered into the current instrument (G-04). It cannot finish until discrepancies are pulled into a spreadsheet, resolved off-platform, scored off-platform (G-03, G-05), and re-typed into a public website index by index (G-02). The platform is absent at exactly the two moments — instrument setup and score publication — where errors are least recoverable.

And the evidence trail is the casualty

Because arbitration and scoring happen in spreadsheets, the reasoning behind a published figure lives outside the system that publishes it. When a Member State queries its rank, the chain from portal observation → assessor answer → discrepancy resolution → published value cannot be reconstructed from the platform. That is a defensibility problem before it is an efficiency problem.

III · The stack question05 / 11

Why continuing on the .NET path is not favourable

Stated precisely, so the argument survives scrutiny: this is not a case against modern .NET as a language or runtime. It is a case against three specific things the current path carries forward — WebForms, the legacy schema, and a procurement-gated single AI vendor.

Terminal
framework

WebForms is a closed road, not an old one

DNN 9.6.1 sits on ASP.NET WebForms, which runs only on .NET Framework 4.x — Windows-only, never ported to .NET Core or .NET 5+. It is maintained, not advanced. Building the next decade of EGDI on it means building on a branch with no forward path; a later migration is not deferred, it is guaranteed.

Inherited
ceiling

The Phase 3 design modernises the hosting, not the constraint

The incumbent technical design pins the target to “compatibility with the Microsoft stack (IIS, SQL Server, .NET)”, extends the legacy EKBSRVY_ tables as its baseline schema, and keeps “UNHQ Active Directory (NOT Azure AD); VPN-based admin access”. Moving that to Azure relocates the server. It does not lift the ceiling — the new system inherits the old system's identity model and data model on day one.

AI as a
phase 3 item

The capability that justifies the rebuild arrives last

The incumbent roadmap places AOSQ in “Phase 3 — Optimization”, after Foundation and after Toolkit. The pre-fill that removes the 60,602-judgement problem is the third thing delivered, not the first. Meanwhile it is bound to a single approved vendor (Azure OpenAI, ARB 2023-158): model selection becomes a procurement decision on an ARB cycle, in a field that re-baselines every few months.

Ecosystem
mismatch

The agentic layer's ecosystem is Python-first. Agent orchestration, headless browser traversal of live government portals, document extraction, retrieval, evaluation harnesses — the working libraries are Python. Implementing that layer in .NET means reimplementing it or bridging to Python anyway, so the stack decision buys a second runtime rather than avoiding one.

Operating
model

Windows / IIS / RDP / VPN constrains delivery, not just runtime. On-premises AD with RDP administration and manual deployments rules out modern SSO and MFA, rules out ordinary CI/CD, and narrows the hiring pool to Windows-server operations — against a project that must be staffed as individually-contracted consultants rather than a vendor team.

API-first, so EGovKB survives

Cycles, questions, units, assessment runs, role-scoped human answers and publication are all addressable over /api/v1. The public knowledge base does not have to be rebuilt to benefit — it can consume the same records the assessor portal writes, which removes G-02 and G-09 without touching EGovKB's front end.

This is the integration surface the Phase 3 design specifies as a requirement. It exists now.

IV · The mechanism that matters08 / 11

Discrepancy handling, in the platform instead of in a spreadsheet

Four seeded demonstration units, each frozen at a different disagreement rate over a 20-indicator slice. The tolerance is the only thing deciding what happens next — and it is a project setting, editable while the project is locked.

The rules that make it defensible

  • —A round opens only once both roles declare complete — a partial assessor cannot trip a false alarm.
  • —One round only. If the assessors do not converge, it force-closes as exhausted and escalates rather than looping.
  • —Arbitration shows the Senior Reviewer both entries — each answer, evidence link and note — so no one decides blind.
  • —A resolved case retains the tolerance in force when it was raised, so a later settings change cannot rewrite history.
  • —Reopening requires a written reason; arbitrating requires a Yes/No on every disputed indicator, enforced server-side.

Against G-05: the current platform has a “% Threshold” field and an instruction to leave it at 20. Nothing reads it.

IV · Governance09 / 11

What the AI is not permitted to do — and how that is enforced

The Phase 3 design sets the right constraint: human-in-the-loop is mandatory, and no AI involvement in official index scoring. We agree entirely. The difference is that we meet it in the first release rather than the third, and we enforce it in the test suite rather than in policy prose.

Human authority, structurally

  • ✓Assessors hold 100% authority to accept, edit or override a suggestion. Human answers take publication precedence unconditionally.
  • ✓Re-running pre-fill preserves every human submission — a re-run cannot overwrite a person's work.
  • ✓Every declined suggestion carries an unambiguous reason: no_usable_evidence, unresolved_disagreement, failed_final_validation, budget_reached. Silence is never a verdict.
  • ✓A per-unit run budget caps spend; the pipeline stops and says so rather than degrading quietly.

Auditability, executably

verify independenceAsserts the two assessor agents never see one another's output — the assumption blind A/B rests on
verify evidenceEvery suggestion traces to a retrieved source
verify resumeAn interrupted batch resumes without duplicating or losing work
verify no-credentialsNo secret has entered the audited configuration snapshot
telemetry costPer-session spend, timings and fetch log

Run pytest -m independence to execute the assertions that make the method defensible. A reviewer can check the claim rather than accept it.

V · Position10 / 11

Recommendation: prove the engine on one cycle before committing to a rewrite

1 · Run in parallel

Take one live cycle — a LOSI city set or a regional OSI slice — through the platform alongside the existing process. Compare published figures against the assessors' own results. The Phase 3 plan already calls for a parallel-run transition period; this uses it as evidence rather than as insurance.

2 · Keep EGovKB

EGovKB stays the public face and consumes /api/v1 instead of hand-typed Value/Rank pairs. That closes the two highest-cost gaps — G-02 and G-09 — with no public-facing change, no migration, and no procurement decision required first.

3 · Defer the .NET rewrite

Nothing above requires resolving the stack question today. It does mean the decision gets made with a working assessment engine in hand and a measured comparison on the table, rather than from a design document alone.

What we can demonstrate now

The full lifecycle end to end, on seeded projects frozen at each state: authoring and lock, blind A/B intake, automatic detection, joint reconciliation, Senior Reviewer arbitration, publication, and the public scorecard. Plus real MSQ ingestion from 50-page Member State submissions and live portal traversal.

What is genuinely not ours to decide

OICT hosting and ARB approval. The final IAM binding. Migration of the historical EKBSRVY_ record — which must happen regardless of stack, and which we should scope early because it is the one piece of work no architecture choice makes easier. We are not proposing to pre-empt any of these.
